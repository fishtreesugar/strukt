# Schemas

Strukt builds on `Ecto.Schema`, so much of what you need to know can be found in the 
[Ecto docs](https://hexdocs.pm/ecto). However, there are a few quality-of-life improvements
implemented in Strukt that extend the schema syntax to allow for some additional functionality.

## Schema Extensions

The following is list of the changes we've made to the syntax provided by `Ecto.Schema`:

* Support for defining validations inline with the field definition, i.e. alongside standard
options provided to `field`/`embeds_one`/`embeds_many`.
* Support for autogenerated fields with `embedded_schema`. Typically autogenerated fields in
Ecto are intended to be provided by the database, but without a database in the loop, nothing
happens. Since we're defining `new/1` for the structs we define, it gives us an opportunity to
ensure that the autogenerated fields get values immediately on struct creation.
* Support for `defstruct`'s extended functionality within `embeds_one`/`embeds_many` inline
definitions, to any arbitrary nesting depth.

The default primary key is an autogenerated `:uuid` of type `Ecto.UUID`. A custom
`@primary_key {:id, :binary_id, autogenerate: true}` also generates a UUID through `new/1`,
including for nested ordinary embeds. A supplied ID takes precedence, even when it is `nil`.
Existing IDs are preserved on partial updates. The built-in `:id` type does not have a
local sequence generator.
Custom ID types with `autogenerate/0` and parameterized ID types with `autogenerate/1` use
their generators. Types backed by `:binary_id` without a generator receive a UUID cast
through their type. A generator shared by several fields runs once; for example,
`inserted_at` and `updated_at` receive the same generated timestamp.

One of the biggest quality-of-life improvements provided here is the ability to express
validations inline with the field definition, as well as the automatic generation of validation
code which is automatically applied when you call `change/2` or `changeset/2`. These build upon
and operate on `Ecto.Changeset`, which is a powerful way of expressing constraints, and they
compose well, especially when you have embeds involved.

## Polymorphic Embeds

Use `polymorphic_embeds_one/2` and `polymorphic_embeds_many/2` to accept multiple declared
schema types in one field. They support Strukt's inline validation options and generated
union types. The [polymorphic embeds guide](polymorphic-embeds.md) covers declarations,
type tags, casting, updates, and JSON.

## Expressing Validations

Let's take a look at the use of inline validation rules, which you pass along with the standard
options to macros like `field/3`. The following validation options are provided:

* `required: boolean | Keyword.t`, options same as `validate_required/3`
* `length: Keyword.t`, options same as `validate_length/3`
* `format: Keyword.t`, options same as `validate_format/4`
* `one_of: list(term) | [values: list(term), message: String.t]`, i.e. `validate_inclusion/4`
* `none_of: list(term) | [values: list(term), message: String.t]`, i.e. `validate_exclusion/4`
* `subset_of: list(term) | [values: list(term), message: String.t]`, i.e. `validate_subset/4`
* `range: Range.t | [value: Range.t, message: String.t]`, i.e. `validate_inclusion/4`
* `number: Keyword.t`, i.e. `validate_number/4`

In all of the above, you can provide a custom validation message using the keyword list variant,
and setting `:message` to the desired format string.

Empty sets are valid declarations: `one_of: []` rejects supplied non-nil values,
`none_of: []` excludes nothing, and `subset_of: []` permits only empty subsets.
These rules still follow Ecto's changed-value validation semantics.

In a named or inline schema, define constants before the fields and functions that use them.
Field options and inline validations capture the constant's value at that field's declaration.
For example, `@allowed ["a", "b"]` can supply `one_of: @allowed` on the next field.
Options are evaluated once, including `primary_key:`; reassigning a constant later does not
change earlier fields. Type declarations such as `@type` can precede these constants.
Aliases and attributes retain their declaration order, including when functions occur
between fields. Schema field settings such as `@schema_redact`, `@field_source_mapper`,
and `@timestamps_opts` apply at each declaration. Functions retain their own attribute
values and may refer to their schema's struct.

Ordinary field and embed options may be keyword literals or expressions such as `@opts`.
`field :name` defaults to `:string`. A schema may contain only attributes, such as
`@primary_key false`, when no fields are needed.

`required: true` and `required: [message: "..."]` enable required validation.
`required: false` disables that inline rule, just like omitting the option. Other validators
and custom `validate/1` callbacks can still impose additional constraints. On `embeds_many`
and `polymorphic_embeds_many`, required validation rejects a missing or empty list.

A module may define its own `changeset/1` or `changeset/2`; Strukt then
skips generating that function. If only `changeset/2` is defined, the generated `changeset/1`
calls it. `new/1` and `change/2` always use the internal `changeset/3`, so they still apply
the schema's casting and validations.

Generated types include `| nil` for optional ordinary fields, even when they have a non-nil
default. Required ordinary fields and single embeds omit `| nil`, including when `required`
uses keyword options. These annotations express validation constraints; constructing a raw
struct or using `from_json/1` does not enforce them. Embed collections use list types for
validated data; see the JSON guide for the polymorphic-list `null` loading exception.
Ordinary arrays and typed maps allow `nil` elements or values during casting, so their
generated element types include `| nil`, even when the container itself is required.
Attribute-defined primary keys and generated timestamps also retain their schema types,
including custom timestamp names and disabled timestamps. The default key is typed
`Ecto.UUID.t() | nil`; default timestamps use `NaiveDateTime.t() | nil`, and UTC timestamps
use `DateTime.t() | nil`. The `:id` type uses `integer()`, matching Ecto's acceptance
of negative values; use a numeric validation if an ID must be nonnegative.

### Custom Validations

If you need to perform custom validation, or express conditional constraints, then you can override
the definition of `validate/1`, which takes an `Ecto.Changeset` on which you can apply arbitrary
validation logic. This callback is also invoked any time you call `new/1`, so be aware that if you need
to conditionally apply validation rules, you will need to be able to determine the condition from
the data the changeset is based on, see the `Ecto.Changeset` API if you aren't sure how to do that.

Module attributes used in a `validation` guard capture their values at that declaration.
For action-dependent child validation, see the [nested validation semantics](usage.md#parameter-names-and-changeset-apis).
