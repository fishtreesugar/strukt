# Usage

This document details further how Strukt is implemented, and how to use it. Please report any issues on the issue tracker.

### Struct Definition

There are two variants, depending on how you want to define your structs, `Strukt.defstruct/1` and `Strukt.defstruct/2`.

The first is used to define a struct associated with the current module being defined:

    defmodule Person do
      use Strukt

      defstruct do
        field :name, :string, required: true
      end

      def name(person), do: person.name
    end

The second is used to define a struct _and_ its module, inline:

    defmodule Entities do
      use Strukt

      defstruct Person do
        field :name, :string, required: true

        def name(person), do: person.name
      end
    end

The latter is generally useful only when you want to define multiple modules in the same file, which is
probably relatively rare, but comes up from time to time, and this reduces the boilerplate a bit.

Lastly, it is worth noting that embedded structs behave almost identically to `Strukt.defstruct/2`:

    defmodule Company do
      use Strukt

      defstruct do
        field :name, :string, required: true

        embeds_many :employees, Employee do
          field :name, :string, required: true
          field :email, :string, required: true, format: ~r/^.+@.+$/

          def name(employee), do: employee.name
        end
      end
    end

In the above, you'd end up with two modules, `Company` and `Company.Employee`. It's generally recommended to
split up the definition of embedded structs, but in simple cases where the embedded type is strictly used only
within the context of the containing type, it may be easier to keep the definitions together like this.

### Working with Structs

The typical usage pattern for structs defined with Strukt more or less falls into one of the following buckets:

* Create a new struct, using the generated `new/1` function, which returns `{:ok, struct}` or `{:error, changeset}`
* Given a struct, and a set of changes, apply them to the struct using `change/2`, producing an `Ecto.Changeset`
* Given an `Ecto.Changeset` representing the struct, get back the struct using `from_changeset/1`,
which like `new/1`, returns `{:ok, struct}` or `{:error, changeset}`

Both `new/1` and `change/2` build on a common changeset function that performs casts for fields and embeds, and
runs all of the validation rules, including custom ones defined in `validate/1`. The primary difference between
the two is that `new/1` also performs autogeneration for fields (if applicable), and automatically invokes `from_changeset/1`
to get back the struct value.

### Omitted Parameters, Nil, and Empty Values

`new/1` and `change/2` accept maps with atom or string keys, keyword lists, and schema structs.
For these two functions, top-level `nil`, `%{}`, and `[]` all mean no supplied fields.
On creation, omitted fields use their defaults and autogenerated values. On update, omitted
fields retain their current values, including pending changes in an existing changeset;
they are not submitted for casting again. Validation still runs.
This also preserves embed changes edited with `Ecto.Changeset.put_embed/3` or removed with
`Ecto.Changeset.delete_change/2`: old embed parameters in the changeset are not replayed
when a later update omits that field.

Explicit field values have different meanings:

| Field kind | Explicit `nil` | Explicit `[]` |
| --- | --- | --- |
| Ordinary `field` | Sets the field to `nil`, even if it has a default | Cast according to the declared type |
| `embeds_one` | Clears the embed | Empty keyword parameters, not a clear operation |
| `polymorphic_embeds_one` | Clears the embed | Invalid input |
| `embeds_many` / `polymorphic_embeds_many` | Normalizes to `[]` and clears the list | Clears the list |

Clearing an ordinary Ecto embed respects `on_replace`. For example, use `on_replace: :delete`
to allow removal; the default `:raise` can raise when removing existing data. Clearing a
required field or embed fails validation. A `nil` element *inside* an embed list is invalid;
it is not a placeholder for keeping the existing element.

For example, given an optional string `name` with `default: "anonymous"`:

    {:ok, person} = Person.new(name: "Ada")
    {:ok, unchanged} = person |> Person.change(%{}) |> Person.from_changeset()
    # unchanged.name == "Ada"
    {:ok, cleared} = person |> Person.change(name: nil) |> Person.from_changeset()
    # cleared.name == nil, not "anonymous"

Defaults only supply missing values; they do not make fields required. Explicit `uuid: nil`
also overrides an autogenerated UUID, including in polymorphic embeds. Updating a polymorphic
primary key to `nil` preserves that value; a required rule on the key can reject it.
Empty strings follow Ecto's casting rules and may be
replaced with the schema default; they are not equivalent to explicit `nil`.

Struct parameters supply all their fields, including `nil` and default values. Use a map or
keyword list when expressing a partial update. Supplied embed lists define the resulting
membership, rather than appending to the current list. Supplied primary keys are cast to their
schema types and matched against current entries of the same module, including pending
changes. If no primary key is supplied, the entry at the same position supplies context.
An explicit nil, invalid, incomplete, or unmatched key never falls back to another entry's
position. Changing a polymorphic entry's type starts with the new type's defaults instead.
Ordinary embed lists whose schema has `@primary_key false` also retain omitted fields by
position. Supply complete values when reordering such lists. Ecto's `on_replace` policy
still applies to the replacement of their entries.

Embed collections also accept indexed maps such as `%{"0" => params, "1" => params}`.
Numeric keys are sorted numerically, so `"2"` precedes `"10"`. The entries follow the same
source-name normalization, autogeneration, and identity matching as list entries; an empty
map clears the collection. Malformed entries return a field error.

### Parameter Names and Changeset APIs

`new/1` and `change/2` map both the schema field name and its `source:` name, including in
nested parameters. If both names occur, the source name wins. For each name, the atom key
wins over the string key. An explicit `nil` counts as a supplied value at every precedence
level; it does not fall back to a different key. Schema structs use their schema field names.

The lower-level `changeset/2` and `changeset/3` APIs accept maps or keyword lists (and a
struct of the same schema), but do not perform source-name normalization or autogeneration.
Use schema field names at every nesting level with these APIs. They apply the same field-level
nil/empty-list rules and validations as `change/2`.
In particular, direct polymorphic changesets leave missing primary keys unset. Use `new/1`
or `change/2` when newly supplied nested records need autogenerated values.

For an ordinary single embed with `on_replace: :update`, direct changeset updates can omit
the primary key and still preserve existing and pending fields. Ordinary embed lists may
mix declared structs and parameter maps in these direct APIs: structs are trusted as already
validated, while maps run the child schema's changeset validations.
Trusted structs update matching existing entries as well as creating new ones. Ordinary
single embeds also require a struct of their declared schema; foreign structs return a
field error.

Nested parameter maps run Strukt child validations with an action already assigned:
`:insert` for new records and `:update` for matched existing records. Ordinary embeds follow
Ecto's replacement actions, so replacing entries without primary keys uses `:insert`.
This makes action guards effective during nested creation as well as direct child creation.
Trusted struct inputs continue to skip child validation. Plain Ecto children retain their
own `changeset/2` callback and its action-handling behavior.

`from_json/1` is a separate loading API, not a substitute for `new/1`. See the
[JSON guide](json.md) for its validation and null-handling differences.

If you need to do custom initialization of your own, then you can override `new/1` yourself, making sure that you
invoke `super(params)` at some point to perform all of the standard initialization logic. For example, if you wanted
to generate a primary key that is based on a hash of the contents of some fields of the struct, you might do something
like this:

    defmodule Thing do
      use Strukt

      defstruct do
        # This overrides the default primary key to disable autogeneration
        field :id, :string, primary_key: true
        field :name, :string, required: true
        field :email, :string, required: true
      end

      def new(params \\ %{})

      def new(params) do
        with {:ok, %__MODULE__{} = thing} <- super(params) do
          hash =
            :crypto.hash(:sha256, :erlang.term_to_binary({thing.name, thing.email}))
            |> Base.encode16(case: :lower)

          {:ok, %__MODULE__{thing | id: hash}}
        end
      end
    end
